02 / Enforcement mechanism

The policy becomes switch behavior.

The REST API is a control surface. The firewall is the OpenFlow table inside s1. A block is considered effective only after the controller sends the rule changes and the real network test confirms them.

↔
Choice 01

Match both directions

A source-only drop can make ping fail by dropping the reply while still allowing the inbound request. Two matches, source and destination, actually isolate h2 for IPv4 traffic.

⇢
Choice 02

Keep forwarding simple

A priority-0 NORMAL action lets OVS perform familiar L2 learning. Ryu handles policy changes rather than every allowed packet.

✓
Choice 03

Wait before acknowledging

A barrier reply gates the API state update. The controller does not put h2 on its blocked list merely because it sent a FlowMod.

Priority decides

Three rows explain the firewall.

OpenFlow selects the highest-priority matching entry. An empty instruction list means drop. The normal rule stays in place while h2 is blocked.

P / 100eth_type=0x0800 · ipv4_src=10.0.0.2DROP
P / 100eth_type=0x0800 · ipv4_dst=10.0.0.2DROP
P / 0all other framesNORMAL
Why priority 100? It outranks the priority-0 forwarding entry. h1→h3 does not match either h2 drop, so it reaches NORMAL. h1→h2 matches the destination drop; h2→h1 matches the source drop.
Per-packet decision

What s1 evaluates for every frame.

The decision occurs inside the switch, independent of a REST status message or controller log line.

01

Inspect EtherType

Only IPv4 frames (0x0800) can match the two drop entries. ARP goes to NORMAL.

02

Compare source and destination IP

If either address is 10.0.0.2, a priority-100 rule wins and discards the frame.

03

Forward everything else

The remaining frames reach priority 0 and use OVS L2 learning and forwarding.

Dynamic change sequence

From API request to switch rule.

Policy state is updated only after the switch reports that it processed the commands in order.

01

Validate the exact client

Ryu accepts IPv4 addresses only for h1, h2, or h3 in 10.0.0.0/24. Bad, out-of-subnet, or unconfigured addresses return 400.

02

Check current policy and switch connection

A duplicate block returns 409; an absent unblock returns 404. If s1 is disconnected, a valid change returns 503.

03

Send two FlowMods and a barrier

Ryu adds or exactly deletes the source and destination matches, then sends OFPBarrierRequest. The two drops have distinct cookies.

04

Commit desired policy

On the barrier reply and without a correlated OpenFlow error, the blocked set changes and REST returns success. The integration test then checks OVS and pings.

State and recovery

Why the controller and switch stay aligned.

Synchronization is a design requirement because the REST list alone cannot prove data-plane enforcement.

Policy memory

Desired state

A controller set records which configured clients should be blocked. It changes only after the switch barrier confirms processing.

Reconnect

Replay

When DPID 1 reconnects, Ryu installs normal forwarding and reapplies the in-memory block policies.

Restart

Cookie cleanup

On switch features, a reserved cookie prefix removes stale firewall rules from a previous controller process before new policy is installed.

!

Boundary of the guarantee. A barrier confirms OpenFlow processing order, not packet behavior by itself. Timeout or error can leave partial switch state. The integration run explicitly read s1's flow table and sent packets to verify enforcement. The policy set is not persisted across controller process restarts.
